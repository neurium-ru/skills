# Frontend-прототипы

Ты собираешь живой веб-прототип, который пользователь открывает в браузере. Ключевая механика: dev-сервер живёт как долгоживущий процесс с понятной ссылкой, а результат ты сам проверяешь глазами в браузере, а не сдаёшь непроверенную вёрстку.

Навык работает в двух средах — определи свою сам. Если рабочая папка — `/workspace` и доступен инструмент `neurium_service`, ты в облачном компьютере Нейриума: сетевое хранилище, сэндбокс, превью у пользователя в панели треда. Если работаешь в папке проекта на машине пользователя — ты в Neurium Desktop: обычный диск, локальный браузер, ни сэндбокса, ни `neurium_service`, ни панели превью.

## Когда применять

- Пользователь просит интерфейс, лендинг, демо, дашборд, интерактивный прототип.
- Нужно быстро показать работающий UI, а не описать его словами.

## Порядок работы

1. **Выбери масштаб скаффолда под задачу.**
   - Небольшая статичная страница или демо одной идеи — один `index.html` (можно с inline CSS/JS). Не тащи сборщик, где он не нужен.
   - Приложение с компонентами, состоянием, роутингом — vite-проект (`npm create vite@latest` через `execute_command`).
2. **Зависимости.** На машине пользователя — обычный `npm install` в папку проекта, никаких mount'ов и `/tmp/deps`. В облаке — на локальный диск, не в `/workspace`: перед первой установкой примонтируй `node_modules`: `mkdir -p /tmp/deps/<имя-проекта> node_modules && { mountpoint -q node_modules || sudo mount --bind /tmp/deps/<имя-проекта> node_modules; }`, затем `npm install` как обычно. Установка прямо в `/workspace` идёт минуты (это сетевое хранилище) и навсегда оставляет там тысячи файлов; симлинк вместо mount не годится — npm заменит его реальной директорией. Если после пересоздания сэндбокса `node_modules` внезапно пуст — повтори mount и переустанови зависимости.
3. **Запусти dev-сервер.** В облаке — управляемым сервисом: `neurium_service` с `action: "create"` (типовой случай — `{ runtime: "node", cwd: "<директория проекта>" }`: команду, порт и health пресет выведет сам). Сервер обязан слушать `0.0.0.0` (для vite — `--host 0.0.0.0` или `server.host` в конфиге): `localhost`/`127.0.0.1` превью не даст. Не запускай серверы через `execute_command background: true` — у такого процесса нет владельца; если всё же запустил, оформи его под управление через `action: "adopt"`. На машине пользователя — обычной командой в фоне (`npm run dev`, `npx vite`) на loopback: ссылка `http://localhost:<порт>`, `0.0.0.0` не нужен; помни, какой процесс ты запустил, и не плоди дубли.
4. **Проверь результат глазами.** В облаке сервис после create виден пользователю в панели «Превью»; открой previewUrl в браузере (`browser_goto`), сделай `browser_snapshot` и `browser_screenshot`, при необходимости покликай (`browser_click`) и проверь адаптивность; упал — смотри `action: "logs"`. На машине пользователя открой `http://localhost:<порт>` в локальном браузере сам и сообщи ссылку пользователю; упал — смотри вывод процесса. Вёрстку принимай визуально, а не по факту «сервер поднялся». Проверяя интерактив (формы, переходы), проверяй смену состояния, а не наличие текста: текст «спасибо за заявку» может присутствовать на странице и до отправки — такой ассерт всегда зелёный и ничего не доказывает.
5. **Доводи вид до аккуратного дефолта.** Даже прототип не должен быть голым html: осмысленные отступы (`spacing`), читаемая типографика, разумная сетка, тёмная тема по умолчанию, если это вписывается. Аккуратный нейтральный вид лучше «браузерных дефолтов».
6. **Прибери за собой.** Когда превью больше не актуально — останови сервер (в облаке — `neurium_service` `action: "stop"` / `"remove"`, на машине пользователя — заверши фоновый процесс). Для многосессионной работы над прототипом предложи пользователю оформить его как экспанс (`neurium_expanse`) — тогда файлы и контекст сохранятся между сессиями; создавай экспанс только с согласия.

> В облаке сервисы и превью работают только в основном (primary) рабочем пространстве. В изолированном auxiliary-биндинге превью недоступно.

## Чеклист качества

- [ ] Масштаб скаффолда соответствует задаче (один html vs vite).
- [ ] Зависимости по среде: в облаке `node_modules` — bind mount на `/tmp/deps/<имя-проекта>`, не в /workspace; на машине пользователя — обычный `npm install` в папку проекта.
- [ ] Dev-сервер по среде: в облаке — управляемый сервис (`neurium_service create`) на `0.0.0.0`; на машине пользователя — фоновый процесс на `localhost`, ссылка открыта в браузере и сообщена пользователю.
- [ ] Результат открыт и проверен в браузере (snapshot + скриншот); проверки интерактива ассертят смену состояния, а не присутствие текста на странице.
- [ ] Вид аккуратный: отступы, типографика, сетка — не голый html.
- [ ] Неактуальный сервер остановлен (сервис удалён / процесс завершён); для долгой работы предложен экспанс.

## Частые ошибки

- **`npm install` прямо в /workspace (облако)** — минуты ожидания и тысячи файлов в облачном хранилище навсегда; сначала bind mount `node_modules` → `/tmp/deps/<имя-проекта>` (симлинк npm снесёт).
- **Bind mount `/tmp/deps` на машине пользователя** — это лечение сетевого хранилища облака; на локальном диске только вредит, ставь как обычно.
- **Сервер на `localhost`/`127.0.0.1` в облаке** — превью не работает, нужен `0.0.0.0`. На машине пользователя наоборот: loopback правильный, а `0.0.0.0` без нужды открывает сервер всей сети.
- **Запуск сервера через `execute_command background: true` в облаке** — процесс без владельца умирает молча; используй `neurium_service`.
- **Сдавать непроверенную вёрстку** — всегда открой в браузере и посмотри.
- **Голый html без стилей** — минимальный аккуратный дизайн обязателен.
- **Тянуть тяжёлый сборщик** для одной статичной страницы.
- **Оставлять висящий сервис** после того, как превью перестало быть нужным.
